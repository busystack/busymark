A2 — CORRECTED IN SOURCE; final verification recorded below.
Independent evidence: separate application processes used the same SQLite path,
while repository guards compared process-local caches and store UPSERTs compared
no persisted input. Startup unconditionally reclassified every syncing note.
Corrections in nextcloud_notes/data/notes_store.dart:
* SQLite transaction ownership now includes expected storage generations for
  account/note/attachment mutations, removal cascades, import and offline state.
  Generation changes commit atomically with durable rows; failure advances neither
  durable content nor the owning cache's expectation. Tombstones fence reuse.
* Observational reads do not silently reauthorize an older repository cache.
  Even no-op editor saves validate their durable identity before claiming success.
* Network workflows acquire an account request claim before sending requests.
  Claims include the cached identities deleted by another process, as well as
  current rows. Stale caches cannot issue a remote delete before validation.
* Session identity includes process ID and Linux process start identity, so
  process ID reuse cannot establish live ownership. Closed sessions release their
  claims; dead sessions are retired. Startup leaves live requests alone and
  recovers interrupted syncing state only when no live request owns it.
* Nested/overlapping request counts live in the SQLite claim transaction; a
  queued begin cannot lose ownership when an earlier request ends.
* Store close drains active requests before releasing ownership. HTTP operations
  never hold a SQLite transaction across a network await.
* Expected-state capture belongs inside the existing startup transaction and
  error handler. Invalid generation metadata now rolls back migration and
  session registration, closes SQLite and reports failure instead of leaving
  open() waiting for an unreported worker failure. The new regression verifies
  the unchanged schema/outbox after failure, immediate lock reuse, repair and
  successful reopen.
Repository synchronize/settings/reconciliation/conflict-resolution/deletion and
attachment-deletion routes use that existing store boundary. This is necessary
ownership state; it replaces neither the repository nor SQLite worker/scheduler.
Behavioral limit: a competing window receives an explicit conflict, keeps its
editor text dirty, and does not automatically rebase or retry the rejected write.
The message directs the user to preserve edits with existing Save As before
reopening the window to reload its cache. New recovery UI or a competing save
engine was not introduced. Uncertain process-identity I/O fails closed, rather than declaring a live owner
dead. Process-start liveness is tested for the supported
Linux desktop, not asserted for other platforms or mixed old/new binaries.
Regression evidence: notes_process_ownership_test uses independent repositories
and actual Dart processes, stale content and same-revision acknowledgment changes,
live-request startup, killed-owner recovery, deleted identities before network
I/O, queued request overlap, attachment/removal/transaction fences and close
during an active request.
Settings widget fixtures explicitly let real SQLite initialization complete
before advancing the fake clock to visual quiescence; existing assertions and
timeout limits remain. The existing Notes suites exercise edits during HTTP acknowledgment, metadata,
settings, creation evidence, uploads, imports, restart, rollback and recovery.

unfolded duplicate indexes. Other fixes restore ownership and recovery rather
than reduce line count. Additional simplification needs an equivalent production
